These guidelines ensure that every Yantra Commons project is consistent, reproducible, and easy for the community to build and improve. Follow them when submitting a new project or when updating an existing one. They apply to schematics, PCB layouts, firmware, enclosures, and documentation alike.

## File Format Requirements

| Asset | Required Format | Notes |
|---|---|---|
| Schematics | KiCad `.kicad_sch` + PDF export | PDF must be legible at A4/Letter size |
| PCB Layout | KiCad `.kicad_pcb` + Gerber ZIP | Gerbers must include all copper, mask, silk, drill, and edge-cuts files |
| BOM | CSV (see columns below) | Must be machine-readable; no merged cells or formatting |
| Firmware | Source code, PlatformIO or Arduino IDE compatible | Include `platformio.ini` or a clearly documented build command |
| Enclosure | STL required; STEP and source file (`.f3d`, `.FCStd`, etc.) recommended | STL must be print-ready with no non-manifold geometry |
| Build Guide | Markdown `BUILD.md` | Must include photos at each major assembly stage |

## Schematic Quality

Your schematic must meet the following requirements before submission:

- All nets must be named — do not leave anonymous wire stubs on buses or between sheets.
- No unconnected pins are permitted without explicit no-connect markers (the `X` symbol in KiCad).
- Power flags must be placed on all power rails to suppress ERC warnings meaningfully.
- Component values must be labeled on all passives — resistors, capacitors, inductors, and crystals.
- Each component must include a manufacturer part number or LCSC part number in its component properties field.

## PCB Layout Standards

Before submitting a PCB layout, confirm the following:

- All components have silkscreen labels that are legible on the fabricated board and do not overlap pads.
- Polarity markers are present for all electrolytic capacitors and diodes.
- The board outline is drawn on the `Edge.Cuts` layer with no gaps.
- Boards larger than 50 mm in any dimension must include at least four M3 mounting holes.
- The KiCad Design Rule Check (DRC) must pass with zero errors — warnings should be reviewed and either resolved or explicitly justified in the README.
- Board dimensions (width × height in mm) must be stated in the README.

## BOM Requirements

Your `BOM.csv` must include the following columns in this order:

```csv
Reference,Description,Value,Footprint,Quantity,LCSC Part #,DigiKey Part #,Mouser Part #,Notes
```

- **Reference** — component reference designator (e.g., `R1`, `C3`, `U2`)
- **Description** — human-readable description (e.g., `100nF bypass capacitor`)
- **Value** — electrical value or part name (e.g., `100nF`, `ATmega328P`)
- **Footprint** — KiCad footprint string
- **Quantity** — integer count of this line item
- **LCSC Part #** — required; enables one-click ordering through JLCPCB/EasyEDA
- **DigiKey Part #** — optional but strongly encouraged
- **Mouser Part #** — optional but strongly encouraged
- **Notes** — substitution notes or sourcing advice, if any

## Documentation Requirements

Every submitted project must include the following files at the root of the repository:

- **`README.md`** — project name and description, difficulty level (Beginner / Intermediate / Advanced), estimated build cost in USD/INR, list of tools required, and at least one photo of a finished build.
- **`BUILD.md`** — step-by-step assembly instructions with photos at each major stage. Instructions must be clear enough for someone at the stated difficulty level to follow without external guidance.
- **`FIRMWARE.md`** — flashing instructions including required software, programmer or bootloader details, and any configuration steps. Required for all projects with programmable components.
- **`LICENSE`** — an appropriate open license file. See [Licensing](/concepts/licensing) for recommended options.

## Naming Conventions

Consistent naming makes the project library easier to navigate for everyone.

- **Repository names** must be lowercase with hyphens and no spaces — for example, `open-air-quality-monitor` or `reflow-oven-controller`.
- **Branch names**: use `main` for the stable, reviewable state of the project; use `dev` for work in progress. Feature branches should be named descriptively, e.g., `add-usb-c-variant`.
- **Release tags**: tag stable releases as `v1.0`, `v1.1`, `v2.0`, and so on. Include release notes summarising what changed.

<Note>
  If you're unsure about any of these requirements, open a discussion on the GitHub repo or ask in the community forum before investing significant design time. Maintainers are happy to review a work-in-progress schematic or layout and flag issues early.
</Note>
